# TolTEC data file and data flow

* The data is collected at a remote site, named "site"

* We have a data processing facility named "server"

* raw data are rsynced from site to server on a daily basis.

* the rsynced raw data on server are stored on an archive drive, in a folder called "data_root"

* There could be multiple data_root. For example, a compute node will checkout data from archive drive to the scratch space, in a new root.

* Historical data are stored in multiple roots on archive based on data batch. (data_root_pre_2024, data_root, data_root_commissioning, etc.)

* raw data are processed by a quick look reduction server running on site.

* generated data products are in the "dataprod_root", a folder on site.

* rsynced raw data are processed by a reduction server running on server.

* generated data products are in the "dataprod_root", a folder on server. 

* On server, there could be multiple dataprod_root, just like there could be multiple data_root

* On site, there is a visualization software, i.e., tolteca_web, that can takes raw data and data products to produce plotly interactive visualizations via dash. The intermediate visualizaiton data pack (json figures, or pickle files, or numpy array dumps) are also formulated as some sort of data product in the dataprod_root.

* On server, the same tolteca_web software is running. This tolteca_web instance can remotely connect to data products produced on site for realtime inspection. In fact, the tolteca_web instance running on site is only for generating the vsiualiaton data products. No one should access the web pages directly on site to save limited bandwidth

# User land

* Toltec support user reduce there data in off-line mode on their computer "local" . Data files are downloaded from the data archive server running on server on local, and tolteca_db should be able to manage the local data_root and dataprod_root on a user computer.


# On the unqiue identifier

raw files generated by the LMT is uniquely (and logicaly) identified by a set of keys.

## Obs-tagged files

These are the primary product of an observation run. The file creation process is controled by a logical entity we refer to as "master". Each file is create by LMT is uniquely identified by the four keys:

    master, obsnum, subobsnum, scannum

This uniquely identifies a "raw obs".

The "official" data files are alwasy written by the master "tcs" (telescope control system).

The LMT hosts a set of instruments, and each instrument has its own "ics" master that can write data files for testing without involving the telescope system.

The tcs obsnums is unqiue site-wide across all instruments.
The ics obsnums is specified to a given instrument.

For a given raw obs, there are a set of files being created, typically one file per "interface"

LMT raw data archive is organized by instrument/master/interface as follows:

    data_lmt:  # the root 
        tel:   # the telescope instrument itself
            tel_toltec, tel_muscat # the telescope interfaces, toltec/muscat are instruments
        toltec:  # the TolTEC instrument
            ics: # the TolTEC ICS
                toltec0, toltec1, ..., hwpr  # the toltec interfaces
            tcs: # the TCS
                toltec0, toltec1, ..., hwpr   # the toltec interfaces
        muscat: # other LMT instruments that we don't support for now

TolTEC instrument generate data files including the following interfaces:

- toltec[0-12]: The 13 detector networks, each network has its own file, generated by the "ROACH" board readout system. nw number and roach number have a one-to-one mapping, i.e., nw0 is read out by roach0, nw1 is read out by roach1, etc. In raw data metadata, we typically refer to the roach number. nw is more tied to the detectors rather than the readout system, so we prefer to use nw when refer to analysis after instrument information is calibrated out in the later stage of the pipeline. There is special cases where we might use different roach to readout a nw, e.g., nw10 might be readout by roach7 because roach10 is not working and we want to test nw10. Due to this confusion, we should primarily use roach when both roach and nw are present. In particular, in raw obsm, roach should be used and nw is derived from roach.

- hwpr: the Half-wave Plate Roatator readout file. The data file looks a lot different from the roach data files. This is why when we organize the raw obs data we refer to the interface name, not the roach number, as there is interface does not roach number at all.

## Time-tagged files

These are ancillary files that are for housekeeping purpose. They are created by a (instrument, interface), and are tagged by a time range.

## Off-site generated files, simulations, etc.

These are files genearted out of context of the telescope/instrument, but are following the convention. Including simulated files, and testing files.


# Requirements on data file and data product management

* dp_raw_obs are logical. The just exist a prior and is immutable. Even for data that are not acquisited yet, in principal they "exist", its it just not acquired yet, in the sense that we can mint the uid using sequential obsnum, subobsnum, and scannum.

*The storage of the actual files can be anywere, remote, local, url, fsspec fs, s3, etc. A data product is "Available" when all/or some of its data_items (per-interface files) as stored in the data prod store is accessible by a user.

* all other data products are derived, meaning that one has to create via some reduction tasks. There can be different results for the same input raw obs, depending on he processing parameter, etc. so we use content_hash to uniquely identify the derived data products.

* The data_items in raw_obs, each data_item (file per interface) can exists in multiple storage location.

* The data_item of derived data products typically is one to one relation, i.e. one entry in tolteca_db corresponding to one directory on filesystem that contains the data items files or a index.yaml file with pointers to data files.

# Special consideration on the tolteca db and tolteca web services

The tolteca_db include a dagster pipeline for prepare data product data base (toltecadb) and data product output (dataprod_toltec). It runs on both site and server, attending to the respective data_lmt root.

The tolteca_web provide a web portal for browsing the data products. It runs on both site and server, because of the data and dataprod root file locality.

Among the four (tolteca_db on site, tolteca_dbx on server, tolteca_web on site, tolteca_web on server):

tolteca_web on site is for debug only. It acceess tolteca_db on site and see dataprod on site as local.

tolteca_db on site ingest the in-operation toltec raw files and prepare the "quicklook" type of data products.

tolteca_db on server sees both server-local data archive and the site-remote data, dataprod, and tolteca_db on site. It should be the most comprehensive one that contains all information regarding the data status.

tolteca_web on server should operate on the tolteca_db on server. It should be the main web portal for users to browse the data products.

* IMPORTANT: the site to server connection is limited. so the server services access site data files via the "partial access" protocal, which for now, is using the zarr file. The data hosted on site visited by server are cached (fsspec layer) and this is important to make sure we don't tax the internet bandwidth.


# Design principles for ORM

## typed metadata, enums, and constants, flags.

Use typed construct through out the codebase. Use AdaptixJSON.

## DataProd table and DataProdSource table

* DataProd table is the minimal unit for data product. Raw obs data (identified by a quartet) is a data product as well.

* DataProdSource table stores information that maps to individual data files, remote or local. A data product can have multiple data sources, and each data source can be stored in multiple locations.

* Location table: location info for data prod source table.

Both the data prod and data prod source tables should provide the column (a meta column containing JSON, or columns, if to be normalized flat) to store typed meta.

## DataProdAssoc table

This is to establish relationship between any data products.

## Registry tables

registry table for everything that are constant. so all types, constants, flags are first class and can have rich descriptions in the db.

Some registries:

flag: flags can have namespace, and a flag string. namespaces: qa, detector, etc.
data_prod_type:  for descriminate data product type
data_prod_assoc_type: for descriminate data product association type
data_prod_kind: : for describing data product data kind (nature of the data itself)

These registries all should have a Python counterpart as typed constructs (enum).

# Some Key design question and answers:

1. Should raw_obs exist as an explicit table?

raw obs is one kind of data product in the data_prod table. We should not make it special. The meta data (typed) is just one type of many matadata.

This does not mean we have to keep the JSON meta column. If we have proof that flat columns is better than json extract, we can opetimize. The key is to use AdaptixJSON to make sure we can establish typed map between Python and database in the ORM layer.

2. Should product metadata use typed JSON (v2.5 approach) or inline columns (v3.x approach)? 

Database table layout is debatable, but typed Python code is a must.

3. Should interface metadata live on data_prod or on the file/source record?

interface (per-file) meta live on data_prod_source table.

4. Should data_prod_type and data_kind be normalized registry tables. All types and constants should use registry.

5. Should associations use directed edges (v2.5)?

Grouped data products is itself a data product. No need to have new table. So, use directed edges. What in v2.5 is missing is the detailed design of how the task processing tables look like.

Assoc between data prod group and data products can be established in many ways, and "processing task" is just one way. Some data product are naturally grouped, such as a focus group, that is a series of raw obs that we vary the telescope M2 mirror position. There is no "processing" associated.

6. Should the flag system use a registry (v2.5) or free-form strings (v3.x)?

Use registry

7. Should tasks have explicit input/output junction tables

Task table related stuff remains more design. for now we can take the easiest way that is to put it as a key in the data prod group meta, describing the task context that generates the data prod group. We can always optimize it later if we find we need more queryablity on the task table.

8. What role should ObsSpec be?

ObsSpec is primarily a domain specific language that help quickly and concisely identify a raw obs (might extend it so it can handle any data product or data prod assoc):

{master/dp_type/dpa_type}-{obsnum}-{subobsnum}-{scannum}-{interface/roach}

A example that this is DSL is that it support wildcard and shortcut in some development version of tolteca package:

{master}-{obsnum}/toltec7  # this query all toltec7 interface of all subobsnum and scannum for the obsnum

This should not be in core part of the ORM. it should live inside the python world as a user-friend construct for input and display. database could have column or meta data entry store it, but it is derived, not primary.
